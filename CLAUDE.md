# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A PWA for managing kids' chores/tasks and reward payouts, with a parent admin console. React + Vite frontend, Supabase (Postgres) as the backend/DB, deployed on Vercel with Vercel serverless functions under `api/`.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run dev:api` — start a local Node server (`scripts/dev-api-server.mjs`) that runs the `api/*.js` Vercel-function handlers directly, needed alongside `npm run dev` for login (and any other `/api/*` call) to work locally. **Both must run together** for local login to work — `vite`'s dev server proxies `/api/*` to this server (see below), but the server itself needs `VITE_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `SUPABASE_JWT_SECRET` in its environment (it does NOT get Vite's automatic `.env.development` loading since it's a plain Node process, not Vite — source `.env.local` and `.env.development` manually before starting it, e.g. `set -a; source .env.local; source .env.development; set +a; npm run dev:api`).
- `npm run build` — production build
- `npm run preview` — preview the production build locally
- No test suite and no lint script are configured in `package.json`.

There IS now a `vite.config.js` at the project root — it's intentionally minimal (just a `server.proxy` entry forwarding `/api` to `dev-api-server.mjs` on port 3001) and deliberately does not import/touch anything from `public/vite.config.js`. That second file still exists and still configures `@vitejs/plugin-react` and `vite-plugin-pwa` (PWA manifest, service worker autoupdate) — but since Vite only loads one root-level config, `public/vite.config.js` is **still not loaded** and the PWA/Workbox setup it describes still has no effect. If PWA behavior seems missing, this is why; don't assume `vite-plugin-pwa` is active. Don't merge the two configs without checking `@vitejs/plugin-react` is actually installed first — it currently isn't in `package.json`.

## Dev vs. production environments

Selected purely by which env file Vite loads — there is no branch-based or CI-based environment split:
- `.env` → production Supabase project (`tvsznlwyvamovdxlpzuc.supabase.co`), used whenever `.env.development` isn't loaded.
- `.env.development` → dev, loaded automatically by `npm run dev` (Vite convention) and overrides `.env`.
- There is no `.env.production`, so `npm run build` only has `.env` to draw from — a production build always targets the production database.
- `api/*.js` serverless functions used to hardcode the **production** URL/anon-key as a fallback when the env var was unset; that's been removed (see below) — they now fail loudly (500) instead. Don't reintroduce that fallback pattern.
- Deployment is Vercel-only (`vercel.json`; no Docker, no CI workflows), auto-deploying on push to `main` (no `.vercel` project-link folder in this checkout — deploys are triggered by pushing to GitHub, not `vercel` CLI). The `cron-tasks.js` Vercel Cron only fires on the Production deployment. A parallel Postgres-side `pg_cron` job (`sql/08_setup_dev_cron.sql`) does the same daily task-generation work for the dev project — the two are redundant by design, not a bug; don't "fix" one without checking the other still makes sense.

**Dev now runs against a local Supabase stack, not a cloud project.** The previous cloud dev project (`gkvxttdjrmczswstfoog.supabase.co`) died from Supabase's free-tier inactivity pause/deletion — a real risk with any free-tier dev project, so don't re-introduce that dependency without considering it'll happen again. Instead:
- Container runtime is **Colima** (Docker-CLI-compatible), installed as standalone user-level binaries in `~/.local/bin` (`colima`, `limactl`/`lima`, `docker`) — no Homebrew, no sudo, no Docker Desktop. Lima's asset files live in `~/.local/share/lima`.
- Colima does **not** auto-start on reboot/login — run `colima start --vm-type vz --arch aarch64 --mount-type virtiofs` before `npm run dev` will work.
- The local stack itself is managed by the Supabase CLI (also a standalone binary in `~/.local/bin`) from the project root: `supabase start` / `supabase stop` / `supabase status`. `supabase init` has already been run once, producing the `supabase/` config directory (currently untracked in git — not yet a repo decision whether to commit it).
- Local endpoints: API `http://127.0.0.1:54321`, direct Postgres `postgresql://postgres:postgres@127.0.0.1:54322/postgres`, Studio (DB admin UI) `http://127.0.0.1:54323`.
- `.env.development` points `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` at that local API URL/anon key.
- No `psql` client is installed on the host — apply/inspect schema `.sql` files by piping into the running container instead: `docker exec -i supabase_db_kids-reward-app psql -U postgres -d postgres -f - < file.sql`.

## Architecture

**Frontend** (`src/`): plain React Router app, no state management library. `src/App.jsx` defines all routes. Auth is still PIN-based UX-wise (name dropdown + 4-digit numpad), but login now goes through `api/login.js` (see below) rather than a direct client-side table query; the logged-in user is cached in `localStorage.user` and a signed JWT in `localStorage.token`. There's no route-guard/context layer — pages read `localStorage` directly, and role gating (e.g. `AdminLayout` redirecting non-`parent` users away from `/admin`) is just a `localStorage.user.role` check in each component. **On local dev, this client-side check is backed by real Row Level Security** (`sql/09_enable_rls.sql`, applied — see below); **production does not have RLS enabled yet** (confirmed still open — the anon key can freely read `users` including `pin` — see Authorization below), so don't treat the client-side check as a real authorization boundary there until it's confirmed live.

- `src/pages/` — kid/parent-facing screens: `Splash`, `Login`, `KidDashboard`, `ParentDashboard`, `ParentTaskManager`.
- `src/admin/` — parent admin console under `/admin`, nested under `AdminLayout` (collapsible sliding sidebar): `AdminTasks` (index), `AdminSettings`, `AdminOccurrences`, `AdminKids`.
- `src/supabaseClient.js` — single shared Supabase client, created from `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`, plus an `accessToken` option that reads `localStorage.token` on every request (supabase-js v2's mechanism for a custom, non-GoTrue JWT) — falls back to anon-only when absent (logged out).
- `src/pushManager.js` — registers `public/push-sw.js` as the push service worker, subscribes via the Web Push API, and persists the subscription to the `push_subscriptions` table.

**Backend** (`api/`, Vercel serverless functions, one file = one endpoint):
- `login.js` — verifies `{name, pin}` server-side against `users` (via `SUPABASE_SERVICE_ROLE_KEY`, bypassing RLS) and mints a 30-day HS256 JWT (`sub`=user id, `role: "authenticated"`, custom claim `app_role`: kid/parent) signed with `SUPABASE_JWT_SECRET`. This is the only way a real Postgres-visible identity gets established — RLS policies key off `auth.uid()` (the JWT's `sub`) and `auth.jwt() ->> 'app_role'`.
- `cron-tasks.js` — daily cron (see `vercel.json`, runs 21:00 UTC) that expands active `tasks` rows into `task_occurrences` for the current day, computed in Riyadh time (UTC+3, hardcoded offset).
- `notify.js` — sends Web Push notifications to users filtered by role/kid id, using subscriptions stored in `push_subscriptions`.
- `trigger_prayer_reminders.js` — fetches Riyadh prayer times from the Aladhan API and fires prayer-related push reminders/sounds.
- `totp.js` — TOTP generate/verify for parent 2FA (`otpauth`).
- `webauthn.js` — WebAuthn registration/authentication backed by `@simplewebauthn/server`, using base64⇄buffer helpers for credential IDs.
- `test.js` — scratch endpoint for probing the `@simplewebauthn/server` export shape.

`totp.js` and `webauthn.js` are not currently wired up to anything in `src/` — a WebAuthn/passkey MFA flow was built and then deliberately reverted back to plain PIN login (see git history around "Temporarily drop MFA / Webauthn requirements"). Treat them as dead code unless a task specifically asks to re-enable MFA.

`login.js`, `cron-tasks.js`, `notify.js`, `trigger_prayer_reminders.js`, and `webauthn.js` each build their own `createClient(...)` (no shared server-side Supabase helper) using `SUPABASE_SERVICE_ROLE_KEY` — they fail loudly (500) if it or `VITE_SUPABASE_URL` is unset, rather than falling back to a hardcoded prod URL/key (that fallback pattern was deliberately removed; don't reintroduce it). `notify.js` and `trigger_prayer_reminders.js` also have the VAPID keypair hardcoded inline rather than read from env.

**Authorization**: Row Level Security is enabled on **local dev only** (`sql/09_enable_rls.sql`, applied) — `parent`-role JWTs get unrestricted cross-kid access on every table (matches the app's existing "parent = admin" model), `kid`-role JWTs are scoped to their own rows, with one real behavioral tightening beyond "close the anon-key hole": a kid can only transition their own `task_occurrences` row `pending → waiting_parent` (the "I Did It!" button), not jump straight to `approved` or touch another kid's row. **`sql/09_enable_rls.sql` has NOT been run on production** — confirmed directly (the anon key still returns full `users` rows, unrestricted). Production's login/auth *code* is fully deployed and working (`api/login.js` uses the service-role key, which bypasses RLS regardless of its state), which can make it look like the security rollout finished — it hasn't. `sql/10_add_reward_types_and_redemptions.sql` (the newer reward-system tables) is applied and RLS-protected on production; the original 6 tables are not. Running `sql/09_enable_rls.sql` against production is still an open action item. One known gap once it is applied: a handful of production's older `task_occurrences` rows predate `kid_id` being populated (only `task_id` was set, relying on a join through `tasks.assigned_kid`) — those specific legacy rows will be invisible to the kid under RLS (parents still see everything). Low severity, historical-only.

**Data model** (see `sql/01_init_new_database.sql` for the base schema, plus the rest of `sql/` in numbered order — applied by hand against both dev and prod, in order, no migration tool):
- `users` — `role` is `'kid' | 'parent'`; PIN is checked server-side in `api/login.js` now (previously a direct client-side query — see git history). Client-side `select('*')` on this table will fail for the `pin` column specifically (column-level grant restriction, dev only) — always select explicit columns (`id,name,role`).
- `tasks` — recurrence rules (`recurrence`, `week_day`, `month_day`) that `api/cron-tasks.js` expands daily. `reward` is now **points**, not currency — UI shows `⭐`, not `ر.س`.
- `task_occurrences` — one row per task per day; `status` moves through `pending → waiting_parent → approved/completed`.
- `wallet_transactions` — **multi-wallet** points ledger. A `wallet` column (`'points' | 'money' | 'screen_time'`) discriminates which balance a row belongs to; there is no stored balance column — a kid's balance in any wallet is always computed client-side by summing this table filtered to that `wallet`. `type` is `'reward'` (task completion, points wallet only), `'convert'` (points→money or points→screen_time, see below), or `'withdraw'` (a wallet request being paid out). `occurrence_id` and `request_id` (both nullable FKs) trace a ledger entry back to the task occurrence or wallet request that caused it.
- **Points is the default/main wallet** — every chore completion credits it (unchanged from before). Kids can freely convert points into the **Money** or **Screen Time** wallets themselves, with **no parent approval** — this is just reallocating already-earned points, done client-side as one atomic multi-row insert into `wallet_transactions` (both legs — the points debit and the target-wallet credit — in a single `.insert([...])` call, both rows or neither). See `KidDashboard.convertPoints`.
- `wallet_rates` — parent-configured conversion rate for each convertible wallet: one row each for `'money'` and `'screen_time'`, with `unit_label` (e.g. `ر.س`, `minute`) and `points_per_unit`. Edited via `/admin` → Settings (`AdminSettings.jsx`). Kids can `SELECT` (read-only) so the UI can show live rates.
- `money_destinations` — parent-managed list of where a Money-wallet payout can go (Cash, Bank Account, School Canteen Wallet, ...). Kids can only `SELECT` rows where `active = true`.
- `wallet_requests` — a kid's request to spend **from** their Money or Screen Time wallet balance (never from Points directly — see above). For `wallet = 'money'`, `destination_id` (FK `money_destinations`) is set and `scheduled_date` is null; for `wallet = 'screen_time'`, `scheduled_date` is set (today/tomorrow/a specific day) and `destination_id` is null. `status` is `pending → approved → fulfilled` (or `rejected` from `pending`). **`approved` and `fulfilled` are deliberately distinct**: `approved` means the parent agreed and the wallet balance was deducted (`wallet_transactions` insert happens here, in `ParentDashboard.approveRequest`); `fulfilled` means the parent has actually completed the real-world action (handed over cash, done the bank transfer, actually let the kid use the screen time — tracked via `fulfilled_at`/`fulfilled_by_name`, set in `ParentDashboard.fulfillRequest`). Don't collapse these back into one step — that distinction is the whole point of this table. `ParentDashboard.approveRequest` also fires two push notifications on approval (confirmation to the kid, reminder to the parent) — there's deliberately no automatic device-side enforcement of Money payouts or Screen Time grants; both platforms' remote-grant APIs are locked to third parties, so the parent always completes the real-world action manually (hand over cash, do the bank transfer, adjust Screen Time/Family Link) after the reminder.
- `push_subscriptions` — one row per `(user_id, subscription)`, used by `notify.js`.

An earlier version of this feature (`reward_types` + a `redemptions` table, one flat list of reward types each directly convertible from points) was built, then replaced same-session once the real requirement — persistent per-kid Money/Screen-Time wallet balances, not a single-step spend — became clear. `sql/10_add_reward_types_and_redemptions.sql` reflects only the current, correct design; the earlier attempt was never applied to production and isn't otherwise recorded.

**`sql/`**: every hand-applied schema file, numbered in the order they must be run (01 through 10 currently) — apply a fresh database (local or otherwise) by running them in that numeric order. `02_create_notifications_table.sql` is redundant with `01_init_new_database.sql` (both create `push_subscriptions`) and can be skipped when bootstrapping fresh; it's kept for history. `04_prayer_reminders_setup.sql`'s `pg_net`/`cron.schedule` webhook lines point at a real deployed Vercel URL — think about whether you actually want that live before re-running them somewhere new.

**Loose one-off scripts**: `temp_scripts/` holds ad hoc maintenance/debug scripts run manually against Supabase (`backfill_names.js`, `check_sql.js`, `sync_prod_to_dev.js`, etc.) — they aren't part of the app build or wired into any npm script. Previously several of these lived at repo root; they've been consolidated into `temp_scripts/`.

## Notes for changes here

- Timezone-sensitive logic (task generation, prayer reminders) assumes Riyadh time via a hardcoded UTC+3 offset or `Asia/Riyadh` — match that convention rather than introducing `Date` logic that assumes UTC or local server time.
- `.gitignore`'s `.env*` pattern was previously broken (saved as UTF-16, so git never matched it) and `.env`/`.env.development` were tracked; this was fixed in commit `7adc08e` and both files are now correctly untracked/ignored.
- Production has an unexplained `kids` table (confirmed via `information_schema.tables` during the RLS/reward-system rollout) that appears nowhere in `sql/`, in git history, or anywhere else this codebase references it. Nothing in the app touches it. Not investigated further — if you're touching schema and see it, don't assume you know what it's for.
